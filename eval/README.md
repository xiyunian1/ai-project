# Text-to-SQL 分析 Agent 评测

用一套固定的数据库和测试集，量化"分析助手"把自然语言问题转成 SQL 并给出结论的准确率，
用来对比不同 Agent 实现，并保证每次改动都有数据支撑。

## 结论

| 配置 | 运行次数 | 执行准确率 | 回答准确率 | 运行出错 | 模型调用次数 | 输入/输出 token | 耗时 P50 / P95 |
|---|---|---|---|---|---|---|---|
| 原实现（JSON 文本动作） | 3 × 100 条 | 70.3%（69–71） | 81.7%（81–83） | 2.0 | 2.30 | 2527 / 1369 | 5.2s / 15.0s |
| 原实现 + 修复提示词乱码 | 1 × 100 条 | 57.0% | 74.0% | 6.0 | 2.27 | 2463 / 1343 | 4.8s / 14.6s |
| 原生 Function Calling v1 | 1 × 100 条 | 69.0% | 94.0% | 0.0 | 4.82 | 12032 / 932 | 4.8s / 12.8s |
| **原生 Function Calling v2** | 2 × 100 条 | **95.5%（94–97）** | **98.5%（98–99）** | **0.0** | 3.50 | 9545 / 694 | **3.7s / 9.3s** |
| v3：v2 + search_docs 工具（知识库 30 篇） | 1 × 100 条 | 94.0% | 99.0% | 0.0 | 3.55 | 10953 / 803 | 3.7s / 11.5s |

留出集（30 条，调优过程中从未使用）：原实现 66.7% → v2 **100%**，说明改进没有过拟合主测试集。
v3 加入资料检索工具后在主测试集上没有退化（在 v2 的 94–97% 区间内），100 条纯数据问题中只有 4 条调用了 search_docs。

模型均为 DeepSeek V4.1 Flash（`deepseek-flash`），并发 3–4。括号内为多次运行的最低–最高值。
每次运行的完整报告见 [reports/](reports/)，逐条轨迹（每一步的工具调用、SQL、token、耗时）见 [reports/raw/](reports/raw/)。

## 改进过程

**1. 原实现的问题（基线 70%）**：对 31 条失败用例逐条归因：

| 根因 | 约占 |
|---|---|
| 最后执行的 SQL 是探索性查询，正确结论只出现在回答文本里，无法用 SQL 核对 | 11 条 |
| 用 `单据类型 LIKE '%销售%'` 匹配，把销售退货混进销售统计 | 9 条 |
| 不理解库存口径（现有库存只在每个仓库-商品最后一行有值；批次剩余要按批号汇总） | 4 条 |
| SQL 报错直接终止整次分析，模型没有机会修正 | 2 条 |

**2. 修复提示词乱码反而下降 12 个点**：原系统提示词中的中文领域提示因编码错误变成乱码。
修复后模型能读懂"销售类问题优先用 `LIKE '%销售%'`"这条提示并照做，结果把销售退货也算了进去。
这条提示是为旧数据写的，乱码反而让它失效了。结论：提示词里的领域规则依赖数据，必须用评测验证。

**3. v1：原生 Function Calling**（Spring AI 1.1）。工具拆成 `list_tables` / `describe_table` / `run_sql` / `ask_user`：
- `describe_table` 读取 SQL Server 的字段说明（`MS_Description`）、空值数、数值范围和枚举取值，模型按需查询表结构，不再猜列名和取值；
- `run_sql` 出错时把错误信息作为工具结果返回，模型自行修正；运行出错从 2 条降到 0；
- 回答准确率 81% → 94%，但执行准确率没变：模型经常在给出结论的查询之后再并行跑一条核对查询（如查数据日期范围），最后一条 SQL 不再是结论依据。

**4. v2：结论可溯源 + 上下文注入**：
- `run_sql` 增加 `is_final_result` 参数，模型必须标记回答所依据的查询，前端和评测都以它为准；
- 系统提示词注入当前日期和可查询表清单，省去"今年是哪年"的探查和一次 `list_tables` 调用；
- 执行准确率 69% → 95.5%，平均模型调用次数从 4.8 降到 3.5，P95 耗时从 12.8s 降到 9.3s。

v2 剩余的失败都是结果形状问题（例如返回明细行而不是去重商品、多返回一行合计），回答本身正确。

## 数据与测试集

- **数据**：`data/generate_inout.py` 用固定随机种子模拟一家医药流通企业 2026-01 至 2026-09 的出入库流水（7798 行，38 个商品、7 家供应商、8 个客户、3 个仓库），覆盖采购入库、销售出库、销售退货、采购退货、调拨、盘点调整，批次按先进先出出库，含季节性和期末断货。所有名称均为虚构。
- **口径说明**：每个字段的业务含义写在 SQL Server 的 `MS_Description` 中（见 `setup_db.py`）。原实现只读取列名，看不到这些说明；工具调用版本通过 `describe_table` 读取。
- **主测试集** `sql_cases.jsonl`：100 条，分 9 类：单表查找 14、聚合统计 16、分组排名 18、时间口径 16、库存与效期 14、复杂组合 12、多轮追问 5、需要澄清 2、安全拦截 3。
- **留出集** `sql_cases_holdout.jsonl`：30 条，在 v2 调优完成后才编写，未用于任何调优。
- 每条 gold SQL 都在数据库上执行过：结果非空、不超过 200 行，Top-N 类问题在边界处没有并列。

## 评分方式

- **执行准确率**（主指标）：取 Agent 标记为结论依据的查询（未标记时取最后一条成功的查询），把结果集与 gold SQL 的结果比较。比较时忽略列名、列顺序和多余列，数值保留两位小数，"2026-01""1 月"等月份写法统一；题目要求排序时还要求行序一致。
- **回答准确率**（参考指标）：在执行准确率之外，gold 结果很小（≤3 行 ≤3 列）且所有值都出现在回答文本中，也算答对。
- **需要澄清**：Agent 调用了 `ask_user` 才算通过。
- **安全拦截**：没有成功执行任何写操作或系统表查询，且评测前后整张表的校验和不变。

## 复现

```bash
# 1. 启动 SQL Server（Apple Silicon 通过 Rosetta 运行 amd64 镜像）
docker compose -f docker-compose.dev.yml --env-file my-ai/.env up -d

# 2. 准备 Python 环境并初始化数据
python3 -m venv eval/.venv
eval/.venv/bin/pip install -r eval/requirements.txt
eval/.venv/bin/python -I eval/setup_db.py

# 3. 启动后端（读取 my-ai/.env）
my-ai/start-dev.sh

# 4. 运行评测（--agent-mode 可选 json / tools）
eval/.venv/bin/python -I eval/run_sql_eval.py --label tools --agent-mode tools
eval/.venv/bin/python -I eval/run_sql_eval.py --label holdout --cases eval/sql_cases_holdout.jsonl --agent-mode tools

# 5. 汇总多次运行
eval/.venv/bin/python -I eval/compare_reports.py "v2=tools-v2,tools-v2-r2"
```

`my-ai/.env` 需要包含 `MSSQL_SA_PASSWORD`、`DB_PASSWORD`、`JWT_SECRET`、`LLM_API_KEY`、`LLM_MODEL` 和管理员口令，参考 `my-ai/.env.example`。

## 资料问答（RAG）

原实现把当前账号的资料按更新时间整篇拼进上下文（单篇截断 6000 字、总量截断 18000 字）。
资料一多，靠后的文档会被直接截掉，模型看不到。现在改为检索：

- **分块**：按 Markdown 标题和"第 X 章/条"切分，每个分块带上所在的标题路径（如「《效期管理制度》 > 第二章 近效期管理 > 2.1 定义」）；
- **召回**：bge-m3 向量检索（pgvector，HNSW 索引，按账号过滤）与中文二字切分的 BM25 关键词检索，两路结果用 RRF 融合；
- **重排**：bge-reranker-v2-m3 对候选重排，取前 5 个分块交给模型，回答时用 [来源n] 标注依据；
- 向量库不可用时自动回退为原来的整篇拼接，其他功能不受影响。

**评测语料**：10 篇虚构的仓储制度（`knowledge/`，8.7k 字），加上 20 篇由模型生成、与问题无关的公司制度
（`knowledge_distractors/`，34k 字），模拟知识库变大的情况。用例 `rag_cases.jsonl`：40 条有标准答案的问题
（每条标注了依据句和答案关键词）和 3 条资料中没有答案的问题。运行命令：

```bash
eval/.venv/bin/python -I eval/run_rag_eval.py --corpus small --label rag-small
eval/.venv/bin/python -I eval/run_rag_eval.py --corpus large --label rag-large
```

**检索**（依据句出现在返回分块中即命中）：

| 模式 | 小语料 Hit@5 / MRR | 大语料 Hit@5 / MRR |
|---|---|---|
| BM25 关键词 | 95.0% / 0.883 | 95.0% / 0.896 |
| bge-m3 向量 | 100% / 0.988 | 100% / 0.988 |
| 向量 + 关键词（RRF） | 97.5% / 0.958 | 97.5% / 0.961 |
| 向量 + 重排 | 100% / 1.000 | 100% / 1.000 |
| **向量 + 关键词 + 重排（默认）** | **100% / 1.000** | **100% / 1.000** |

**端到端回答**（回答中包含全部答案关键词才算对；无答案问题要求明确说明没找到）：

| 语料 | 上下文方式 | 回答准确率 | 无答案时正确拒答 | 平均输入 token |
|---|---|---|---|---|
| 小（10 篇） | 整篇拼接 | 100% | 3/3 | 5611 |
| 小（10 篇） | 检索 | 100% | 3/3 | **443** |
| 大（30 篇） | 整篇拼接 | **47.5%** | 3/3 | 11111 |
| 大（30 篇） | 检索 | **100%** | 3/3 | **460** |

结论：
- 资料少时整篇拼接也能答对，检索的好处是上下文缩小到约 1/13；资料超过上下文预算后，整篇拼接有一半问题答不上，检索的准确率和上下文长度都不随资料增长而变化。
- 在这批语料上 bge-m3 向量检索已经很强，单独加 BM25 没有提升（RRF 引入了少量噪声），重排后两种召回都达到满分。测试集在重排后已经饱和，区分不出混合检索的价值；混合检索对编号、批号这类精确词的作用需要更难的测试集验证。
- 分块粒度是"条"（平均约 90 字），对这类短条款的制度文件够用；对需要综合多条内容的宽泛问题，可以把同一章下的短条款合并成更大的分块再评测。

### 资料 + 数据：分析 Agent 的 search_docs 工具

分析 Agent 新增 `search_docs` 工具，问题涉及公司制度、标准或审批阈值时，先检索规则再按规则写 SQL。
用例 `sql_cases_docs.jsonl` 共 6 条，例如"按照安全库存标准，株洲前置仓当前哪些商品低于前置仓的安全库存？"——
Agent 需要两次检索（前置仓 = 中心仓同类别标准的 20%、中心仓各类别标准），算出各类别阈值后再查询库存。

| 配置 | 结果 |
|---|---|
| 原实现（JSON 文本动作，无法读取资料） | 0/6：不知道规则，要么没有生成 SQL，要么把全部记录列出来 |
| 原生 Function Calling + search_docs | 3 次运行均为 6/6 |

## 局限

- 只有一张宽表。多表场景下 `list_tables` + 按需 `describe_table` 的优势应更明显，但这里没有验证。
- 只测了一个模型。换模型时用同一套命令重跑即可对比。
- 测试集和字段说明出自同一作者，存在乐观偏差；留出集只能部分缓解。
